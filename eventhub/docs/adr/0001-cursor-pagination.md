# ADR-0001: курсорна пагінація каталогу подій

## Статус

Прийнято · 2026-09-18

## Контекст

Каталог подій EventHub відображає події, що постійно додаються організаторами
й мають дату початку (`startsAt`). Список сортується за датою, і кількість
подій з часом зростатиме — одноразова видача всього масиву стане непридатною
для мобільного клієнта й для мок-сервера, який має віддавати передбачувані,
стабільні відповіді для тестів фронтенду.

Ендпоінт `GET /events` має віддавати дані сторінками, при цьому:

- каталог активно поповнюється між запитами користувача (нові події
  з'являються, старі не видаляються);
- фронтенд повинен мати змогу підвантажувати наступні сторінки без
  дублювання чи пропуску подій, навіть якщо між запитами хтось додав нову
  подію;
- клієнту не потрібен довільний перехід на довільну сторінку (наприклад,
  "сторінка 7") — лише послідовне гортання "показати ще".

## Розглянуті варіанти

### Варіант A. Офсетна пагінація (`page`/`offset` + `limit`)

- Плюси:
  - простіша реалізація на боці клієнта (можна відразу перейти на будь-яку
    сторінку за номером);
  - звичний, широко відомий підхід, легко читається в URL.
- Мінуси:
  - за додавання нової події між запитами користувача частина подій
    "з'їжджає" між сторінками — одні дублюються, інші пропускаються;
  - на великих офсетах продуктивність запиту до реальної БД (у майбутньому
    api-gateway) деградує лінійно з розміром офсету.

### Варіант B. Курсорна пагінація (`cursor` + `limit`, непрозорий курсор)

- Плюси:
  - стабільна видача сторінок навіть при активному додаванні нових подій
    між запитами;
  - курсор непрозорий для клієнта — реалізацію (наприклад, зміну ключа
    сортування) можна змінювати без порушення контракту;
  - природно узгоджується з сортуванням каталогу за `startsAt`.
- Мінуси:
  - неможливий довільний перехід на конкретну сторінку за номером;
  - трохи складніша реалізація на боці сервера (потрібно кодувати/
    декодувати курсор).

## Рішення

Каталог подій використовує курсорну пагінацію: параметр запиту `cursor`
(непрозорий рядок) і `limit` (від 1 до 50, за замовчуванням 20). Відповідь
`EventPage` містить поле `nextCursor` — курсор для наступної сторінки або
`null`, якщо подій більше немає. Курсор кодує позицію в сортуванні за
`startsAt` (та `id` як тай-брейкер для подій з однаковим часом початку).

## Наслідки

**Позитивні**

- Список подій залишається консистентним для клієнта навіть при активному
  додаванні нових подій організаторами між запитами.
- Контракт (`openapi.yaml`) не прив'язує клієнта до внутрішньої реалізації
  збереження даних — курсор можна перекодувати без breaking change.
- Мок-сервер (Prism) вже коректно віддає приклад із `nextCursor`, що
  дозволяє фронтенду розробляти підвантаження "показати ще" незалежно від
  готовності реального `api-gateway`.

**Негативні й компроміси**

- Неможливо реалізувати UI з номерами сторінок або переходом "на сторінку N" —
  тільки послідовне гортання вперед.
- Курсор потрібно ретельно тестувати на межових випадках (кілька подій з
  однаковим `startsAt`), інакше можливі пропуски або дублікати на межі
  сторінки.
- Складніше налагоджувати вручну через curl/Postman — курсор непрозорий і
  його не можна підставити "на око", лише скопіювати з попередньої відповіді.

**Що доведеться переглянути, якщо…**

- З'явиться вимога переходу на довільну сторінку (наприклад, для
  адміністративної панелі організатора) — тоді для цього окремого сценарію
  доведеться додати офсетний ендпоінт або гібридний підхід.
- Сортування каталогу перестане бути монотонним за одним полем (наприклад,
  з'явиться персоналізоване ранжування) — курсор на основі `(startsAt, id)`
  перестане бути коректним і потребуватиме перегляду формату.
